# Repository Governance Templates, Expanded Operator Skills, YAML-First Configuration, Human-First Documentation, and Branded Hugo Site

- **Status**: Shipped
- **Type**: Feature
- **Date**: 2026-11-12
- **Owners**: `@loopwright/cli`, `@loopwright/github-app`, `@loopwright/decisions`, `LICENSE`, `.github/`, `.agents/skills/`, `docs/`, `site/`, `scripts/`, `examples/`

## Motivation

Loopwright provides a complete nine-package TypeScript harness and GitHub Action/App control plane (`@loopwright/core`, `@loopwright/state`, `@loopwright/agent-pi`, `@loopwright/controller`, `@loopwright/taskpack-runner`, `@loopwright/memory`, `@loopwright/decisions`, `@loopwright/github-app`, and `@loopwright/cli`), repository skills under `.agents/skills/`, 21 documentation pages under `docs/`, and a Hugo static documentation site under `site/`. However, ten operational and human-experience gaps remain before external repository operators and contributors adopt Loopwright at scale:

1. **Missing Apache 2.0 `LICENSE`, GitHub Issue/PR Templates, and Repository CI/CD Workflows (`LICENSE`, `.github/`)**:
   - The repository lacks a root Apache License 2.0 `LICENSE` file, `.github/ISSUE_TEMPLATE/` forms, `.github/PULL_REQUEST_TEMPLATE.md` guiding issue classification, reproduction steps, conventional pull-request metadata (`/kind`, `/area`), issue linking (`Fixes`/`Addresses`/`Relates`), and Developer Certificate of Origin (`Signed-off-by`) sign-off, as well as GitHub Actions CI/CD workflows (`.github/workflows/{ci,test,docs,code-review,site}.yml`) aligned with `gpustack/loopwright` while keeping `.github/workflows/` strictly protected against untrusted taskpack and sandbox writes.
2. **Under-Specified Documentation Skill and Linter (`loopwright-docs` and `scripts/check-docs.mjs`)**:
   - `.agents/skills/loopwright-docs/` currently provides only high-level bullet points rather than enforceable human-first writing rules (80% ASD-STE100 sentence bounds, active voice, Macro annotated Pretty YAML + Micro `<= 20`-word constraint bullets and uniform 2D tables, `<= 4`-word / `<= 32`-character heading caps, `1–3`-word table headers without articles/demonstratives/interrogatives, `<= 5`-line / `<= 500`-character prose paragraph caps, `<= 10` `##` section caps, SVG diagram + hidden Mermaid parity, and zero AI prose filler), and lacks a canonical `references/page-map.md`.
   - `scripts/check-docs.mjs` enforces structural index alignment and banned words, but does not yet enforce heading length caps, table-header grammar, prose paragraph bounds, section/line caps, Pretty YAML embedded-JSON detection, or a non-blocking `--report` audit mode.
3. **Under-Specified Issue and PR Skill (`loopwright-issue-pr`)**:
   - `.agents/skills/loopwright-issue-pr/SKILL.md` lacks explicit rules for issue prefixes and `<= 80`-character title limits, GitHub web-only YAML frontmatter pitfalls (`gh issue create --label --type` requirement and `mcp__github__create_issue` prohibition), Conventional-Commit PR titles, `/kind` and `/area` commands, issue-linking semantics (`Fixes` vs `Addresses` vs `Relates`), DCO sign-off, and clean commit/PR provenance.
4. **Under-Specified Release Skill (`loopwright-release`) and Missing Explicit-Only Agent Policy (`agents/openai.yaml`)**:
   - `.agents/skills/loopwright-release/` lacks `.agents/skills/loopwright-release/agents/openai.yaml` (`policy.allow_implicit_invocation: false`) and `disable-model-invocation: true` frontmatter, SemVer2 validation (`^v[0-9]+\.[0-9]+\.[0-9]+(-rc[0-9]+)?$`), Interactive / Auto / Unpublished-tag recovery modes, and a deterministic Phase 0–7 release runbook gated on Loopwright's verification suite and explicit user confirmation before any tag or release publication.
5. **Under-Specified Code Review Skill (`loopwright-code-review`)**:
   - `.agents/skills/loopwright-code-review/SKILL.md` lacks separate `## Standards` and `## Spec` review axes, a structured 6-step procedure, five Loopwright-specific engineering axes (architecture/module boundaries, contract compatibility, runtime/lease/process safety, failure/diagnostic discipline, and test evidence), an over-engineering pass (`delete:`, `reuse:`, `stdlib:`, `native:`, `yagni:`, `merge:`, `shrink:`), OpenCodeReview severity mapping (`Critical`/`High`/`Medium`/`Low` to `Blocking`/`Important`/`Nit`), honesty rules, and named noise exclusions.
6. **Dense, Machine-Slanted Documentation (`README.md`, `docs/`, `examples/`)**:
   - Existing `docs/` pages pack dense implementation prose and JSON configuration snippets rather than decomposing complex architecture and operational flows for human readers first with clear progressive disclosure, annotated two-space Pretty YAML configuration blocks, scannable tables, and crisp visual diagrams.
7. **Contributor Internals and Implementation Details Exposed on Public Documentation Site (`docs/` vs `site/`)**:
   - The public Hugo documentation site (`site/`) currently exposes `Contribute`, `Architecture Decisions` (`adr/*`), and low-level internal module pages (`identity`, `evidence`, `state`, `pi-adapter`, `runner-taskpack`, `memory`, `github-app`, `closure-matrix`) alongside user-facing configuration and operational guides, and renders terse unannotated `**See also**:` / `**Next**:` footers instead of two-column descriptive cards.
   - Code-level implementation details belong under `docs/contribute/` (plus `docs/development.md` and `docs/adr/` in repository `docs/`), whereas `site/` must present a clean, simple user/operator panel of **9 pages across 4 groups** (`Getting Started`, `Operations`, `Walkthroughs`, `Configuration`) with complete Pretty YAML configuration blocks, enum value tables beneath YAML blocks, and descriptive `---` + `**See also** — ...` + `**Next** → ...` footers.
8. **Placeholder Site Emblem and Unbranded Palette (`site/` and `README.md`)**:
   - `site/` currently uses a minimal two-color SVG placeholder logo and generic slate-blue accent colors rather than Loopwright's official circular celestial-artisan emblem (`logo.png`) and its Indigo-Violet (`#5B4B9E`) → Teal-Cyan (`#3B8EA5`) → Warm Amber-Gold (`#D89B48`) palette and hero banner design across light and dark modes.
9. **JSON-Heavy Human Configuration Surfaces**:
   - Even though `@loopwright/controller` already natively parses `.yaml` and `.yml` for `ControllerConfig` and `TrustedRegistry` under strict YAML 1.2 core schema rules, human-facing configuration generators and loaders still emit or require JSON in several places: `loopwright init` writes `controller.draft.json` and `registry.draft.json`; `@loopwright/github-app` compiles `registry.json` and `config.json` in `runGitHubActionEntrypoint` and lacks a declarative `github-app.yaml` loader and `.loopwright/taskpack.yaml` `spec.decisions` block; `@loopwright/decisions` lacks a standalone `decisions.yaml` file/bytes loader; and `examples/` and `docs/` present JSON configuration blocks instead of human-friendly YAML.

## Goals

1. Add a root Apache License 2.0 `LICENSE` file, GitHub repository issue templates (`.github/ISSUE_TEMPLATE/{BUG_REPORT,CLEANUP,DOCUMENTATION,ENHANCEMENT,SUPPORT,TODO}.md`), pull request template (`.github/PULL_REQUEST_TEMPLATE.md`), and `gpustack/loopwright` CI/CD workflows (`.github/workflows/{ci,test,docs,code-review,site}.yml`) tailored to Loopwright's nine-package architecture while keeping `.github/workflows/` protected from untrusted taskpack and sandbox writes.
2. Expand `.agents/skills/loopwright-{docs,issue-pr,release,code-review,overview}` (including `loopwright-docs/references/{conventions,page-map}.md` and `loopwright-release/agents/openai.yaml`) and upgrade `scripts/check-docs.mjs` (`--strict` default and `--report` audit mode) to enforce all structural, prose, heading, table-header, section-count, line-cap, and Pretty YAML constraints.
3. Make YAML the primary human configuration format, unify all document `apiVersion` strings to `loopwright.dev/v1alpha1` (disambiguated by `kind`), and deliver a turnkey operator experience across `@loopwright/controller` (`CONTROLLER_API_VERSION = 'loopwright.dev/v1alpha1'`), `@loopwright/taskpack-runner`, `@loopwright/cli` (`controller.draft.yaml`, `registry.draft.yaml`, and `loopwright app-serve --config github-app.yaml [--repo DIR] [--json]`), `@loopwright/github-app` (`registry.yaml` and `config.yaml` artifacts, `spec.decisions` in `.loopwright/taskpack.yaml`, `.yaml`/`.yml`/`.json` proposal paths, `loadGitHubAppConfig`, `createGitHubRestTokenTransport`, and `startConfiguredGitHubApp`), `@loopwright/decisions` (`parseDecisionPolicyDocument` and `loadDecisionPolicyFile` for `decisions.yaml`), and `examples/task.yaml`, while preserving full `.json` backward compatibility and leaving `packages/{core,state,agent-pi}` and `examples/*.json` untouched.
4. Separate `docs/` (full contributor & implementation details under `docs/contribute/`, `docs/development.md`, and `docs/adr/`) from Hugo `site/` (curating **10 user/operator pages across 4 clean sidebar groups**: `Getting Started`, `Operations`, `Walkthroughs`, and `Configuration`, aligned with `https://github.com/gpustack/loopwright`, with zero broken links and zero `Contribute` or `Architecture Decisions` noise).
5. Adopt Loopwright's official RGBA circular emblem (`site/assets/images/logo.png` and `docs/assets/logo.png`) and redesign `site/` light/dark palettes and home hero banner around the logo's Indigo-Violet, Teal-Cyan, and Warm Amber-Gold palette.
6. Rewrite `README.md`, `docs/README.md`, all 22 `docs/**/*.md` pages (10 public `site/` pages + 12 repository-only contributor/ADR pages), `docs/assets/diagrams/*.svg`, and `examples/{README.md,controller.md}` with complete Pretty YAML configuration blocks, domain-grouped configuration tables, explicit enum value tables below YAML blocks, descriptive `---` + `**See also** — ...` + `**Next** → ...` footers rendered via `article-content.html`, and 100% compliance with strict `npm run lint:docs` and `npm run site`.

## Non-Goals

- Modifying any source, test, or qualification files in `packages/core`, `packages/state`, or `packages/agent-pi`, modifying `packages/controller` beyond unifying `CONTROLLER_API_VERSION` to `'loopwright.dev/v1alpha1'`, or modifying existing JSON fixtures under `examples/*.json` pinned by core integration tests.
- Removing backward-compatible `.json` parsing support in loaders that accept both YAML and JSON, or relaxing untrusted taskpack/sandbox write denials on `.github/workflows/`.
- Executing remote `git push`, remote tag creation, GitHub Release creation, or npm package publication without explicit operator instruction.

## User Stories

1. **As a repository operator adopting Loopwright**, I can run `loopwright init --directory ./drafts` to generate two-space `controller.draft.yaml` and `registry.draft.yaml`, launch a turnkey GitHub App HTTP control plane via `loopwright app-serve --config github-app.yaml`, configure `decisions.yaml` and `.loopwright/taskpack.yaml` (including `spec.decisions`) purely in YAML, and copy working YAML snippets directly from `docs/`.
2. **As a human reader browsing the Loopwright documentation site**, I land on a cohesive branded site featuring the Loopwright emblem, clear visual hierarchy, decomposed step-by-step operational guides without contributor-only noise in the navigation, and copy-pasteable annotated YAML configurations with enum option tables.
3. **As a contributor or coding agent**, I can rely on `.github/` templates, `.github/workflows/{ci,test,docs,code-review,site}.yml`, `loopwright-{overview,docs,code-review,issue-pr,release}` skills, and `npm run lint:docs` + `npm run site` to author, review, and ship changes against deterministic, machine-checked standards.

## Proposed Design

### 1. Root `LICENSE` (Apache 2.0), `.github/` Issue & PR Templates, and CI/CD Workflows (`gpustack/loopwright`)

Create the root `LICENSE` file containing the full canonical Apache License, Version 2.0 (January 2004) text with `Copyright 2026 The Loopwright Authors`, seven Markdown templates under `.github/`, and five GitHub Actions workflows under `.github/workflows/` modeled on `gpustack`:

- `.github/ISSUE_TEMPLATE/BUG_REPORT.md`: YAML frontmatter (`name: Bug Report`, `about: Report a reproducible defect in Loopwright`, `title: "[Bug] "`, `labels: ["bug"]`) + sections `### Steps to Reproduce`, `### Actual Behavior`, `### Expected Behavior`, `### Environment` (Loopwright version/commit, Node.js version, OS/kernel sandbox availability, execution surface `cli` / `github-action` / `github-app`), and `### Additional Context` (redacted logs/diagnostics reminder).
- `.github/ISSUE_TEMPLATE/ENHANCEMENT.md`: YAML frontmatter (`name: Enhancement`, `about: Propose a bounded feature or capability improvement`, `title: "[Feat] "`, `labels: ["enhancement"]`) + sections `### Problem / Motivation`, `### Proposed Change`, `### Authority & Safety Boundary Impact`, and `### Alternatives Considered`.
- `.github/ISSUE_TEMPLATE/DOCUMENTATION.md`: YAML frontmatter (`name: Documentation`, `about: Report a gap or inaccuracy in docs/ or site/`, `title: "[Docs] "`, `labels: ["documentation"]`) + sections `### Affected Page(s)`, `### Issue Description`, and `### Suggested Improvement`.
- `.github/ISSUE_TEMPLATE/CLEANUP.md`: YAML frontmatter (`name: Cleanup`, `about: Refactor, dead-code removal, or test/tooling hygiene`, `title: "[Cleanup] "`, `labels: ["cleanup"]`) + sections `### Target Scope`, `### Rationale`, and `### Verification Plan`.
- `.github/ISSUE_TEMPLATE/SUPPORT.md`: YAML frontmatter (`name: Support`, `about: Ask an operational question about Loopwright`, `title: "[Question] "`, `labels: ["question"]`) + sections `### Question`, `### Configuration / Surface`, and `### What You Tried`.
- `.github/ISSUE_TEMPLATE/TODO.md`: YAML frontmatter (`name: Engineering Task`, `about: Track a scoped follow-up engineering task`, `title: "[TODO] "`, `labels: ["todo"]`) + sections `### Objective`, `### Acceptance Criteria`, and `### Owning Package(s)`.
- `.github/PULL_REQUEST_TEMPLATE.md`:
  - `## Summary` (why the change is needed, approach, and any contract/upgrade impact).
  - `/kind <bug|feature|cleanup|documentation|design>` and `/area <core|state|agent-pi|controller|taskpack-runner|memory|decisions|github-app|cli|docs|site>`.
  - `## Related Issues` (`Fixes #...`, `Addresses #...`, or `Relates #...`).
  - `## Verification` checklist (`npm run build`, `npm run typecheck`, `npm run lint`, `npm run lint:docs`, `npm run site`, focused/workspace tests, and `Signed-off-by` DCO confirmation).
- `.github/workflows/` (`gpustack`-aligned CI/CD suite on `gpustack/loopwright`, least-privilege `permissions`):
  - `ci.yml`: `workflow_dispatch`, `push` (`main`, `v*-dev`, tags `v*`, `paths-ignore` for docs/images), `pull_request` (`main`, `v*-dev`). Runs `verify` on `ubuntu-24.04` (Node `26`, `npm ci`, `npm run build`, `npm run typecheck`, `npm run lint`, `node packages/cli/dist/main.js closure --verify-failures`, plus release tarball and `scripts/pack-npm.mjs` `@gpustack/loopwright` bundle upload on `refs/tags/v*`), `release` (`if: startsWith(github.ref, 'refs/tags/v')`, `needs: [verify]`, `permissions: { contents: write }`, `mikepenz/release-changelog-builder-action@v5` + `softprops/action-gh-release@v2`), and `publish-npm` (`if: startsWith(github.ref, 'refs/tags/v') && github.repository == 'gpustack/loopwright'`, `needs: [verify]`, `permissions: { contents: read, id-token: write }`, aligned with `gpustack/core-ui` npm Trusted Publishers OIDC + idempotent `npm view` check + `npm publish --provenance --access public --ignore-scripts` for the single bundled CLI package `@gpustack/loopwright`, keeping all 9 internal `@loopwright/*` workspace subpackages `"private": true`).
  - `test.yml`: `workflow_dispatch`, `push` & `pull_request` (`main`, `v*-dev`, `concurrency` cancellation), matrix across `ubuntu-24.04`, `ubuntu-24.04-arm`, and `macos-15` (`fail-fast: false`, Node `26`), pre-creating `.claude/s04-qualification` and running `npm ci`, `npm run build`, and `npm test`.
  - `docs.yml`: `workflow_dispatch`, `push` & `pull_request` on docs/site/markdown/workflow paths; installs Node `26` and Hugo extended `0.152.2`, runs `npm ci`, `npm run lint:docs`, `npm run site` (`HUGO_PARAMS_VERSION: main`, `HUGO_PARAMS_SOURCEREF: ${{ github.sha }}`), `check-docs-rules` + `docs-and-site` tests, and `.github/**/*.md` link checks.
  - `code-review.yml`: `pull_request_target: [opened, synchronize, reopened]` + `issue_comment: [created]`, `permissions: { contents: read, pull-requests: write }`, invoking `gpustack/.github/.github/workflows/code-review.yml@main` with `CI_GPUSTACK_CODEREVIEW_*` org variables and secrets.
  - `site.yml`: `push` (`branches: [main]`, `tags: ["v*"]`) + `workflow_dispatch` (`if: github.repository == 'gpustack/loopwright'`), building `npm run site` with Hugo extended `0.152.2` and deploying `site/public` to GitHub Pages (`actions/configure-pages@v5`, `actions/upload-pages-artifact@v3`, `actions/deploy-pages@v4`).

### 2. Expanded `loopwright-*` Repository Skills and Docs Linter (`scripts/check-docs.mjs`)

#### 2.1 `loopwright-docs` (`.agents/skills/loopwright-docs/`)
- Expand `SKILL.md` with clear triggers, workflow steps (`page-map.md` lookup -> `conventions.md` authoring -> `docs/README.md` / `site/data/navigation.yaml` sync -> `npm run lint:docs` + `npm run site`), prohibited edits (`specs/` are owned by specification workflow, never rewritten as user docs; `Contribute` pages stay out of `site/`), and strict verification commands.
- Expand `references/conventions.md` to codify human-first technical documentation rules:
  1. **Audience & Decomposition First**: Write for human operators and engineers first. Decompose multi-part concepts into a concise plain-language mental model (1–3 short sentences), a visual flow or lifecycle table, an annotated Pretty YAML macro example, and micro constraint bullets/tables. Never dump wall-of-text paragraphs or raw schema prose.
  2. **Sentence & Voice Discipline (80% ASD-STE100)**: Active voice (`Controller rejects stale leases`, not `Stale leases are rejected by the controller`), imperative procedures (`Step 1: Generate draft configs`), `<= 20` words for procedural sentences, `<= 25` words for conceptual sentences, one action per step, consistent terminology (`task contract`, `lease fence`, `gate token`, `taskpack`, `decision router`, `closure matrix`), and zero AI filler/puffery (`seamlessly`, `robust`, `comprehensive`, `leverage`, `utilize`, `delve`, `tapestry`, `streamline`, `cutting-edge`, `empower`, `unlock`, `it is worth noting`, `in order to`, `this page describes`).
  3. **Macro + Micro Configuration Pattern (Complete Pretty YAML + Enum Value Tables)**: Every configuration surface (`controller.draft.yaml`, `registry.draft.yaml`, `.loopwright/taskpack.yaml`, `github-app.yaml`, `decisions.yaml`, `examples/task.yaml`, consumer GitHub Action YAML) presents a **complete, realistic two-space Pretty YAML** block with inline `#` grouping/constraint comments (Macro view), followed immediately by `<= 20`-word constraint bullets and **uniform 2D Enum / Allowed-Value Markdown tables** (`Value | Meaning | Constraints`) enumerating allowed option values (Micro view). Never embed multi-line JSON strings inside YAML scalars (`config: | { ... }`), never emit JSON config dumps in `docs/` or `examples/*.md` where YAML is supported, and never use nested bullet lists inside configuration sections.
  4. **Page Shape & Caps**:
     - Exact H1 `# <Title>` matching `docs/README.md` `## All pages`.
     - 1–3 intro paragraphs (`<= 5` lines and `<= 500` chars per prose paragraph) before `## Contents`.
     - `## Contents` mirroring all `## ` H2 headings in exact order.
     - `<= 10` `##` H2 sections per page (`<= 8` recommended).
     - Page line caps: `getting-started/architecture.md <= 200` lines; operational/walkthrough/configuration/contributor pages `<= 400` lines; ADR pages `<= 220` lines.
     - Heading caps (`##`, `###`, `####`): `<= 4` words and `<= 32` characters (`Step N: <Action>` counts words after `Step N:` as `<= 4` words / `<= 38` total chars), zero interrogatives (`what`, `where`, `when`, `how`, `which`, `why`, `who`, `whose`, `whom`).
     - Table headers: `1–3` words (`<= 24` chars) per column header, banning articles (`a`, `an`, `the`), demonstratives (`this`, `that`, `these`, `those`), and interrogatives. Every row in a table must have identical column count, and no cell may exceed `180` characters.
     - Reading Footer (`gpustack` 2-Column Card Pattern): Every non-index `docs/**/*.md` page ends with a horizontal rule `\n---\n` followed by:
       - `**See also** — [Page Title](path.md) (concise scope or boundary reason) · [Second Page](other.md) (specific contract or workflow)` (rendered as a two-column `.related-pages` grid by `site/layouts/partials/article-content.html`).
       - `**Next** → [Next Page](next.md) — one clear action sentence explaining what to configure or read next.` (required on all 10 public `site/` pages; rendered as `.next-page` with `→` by `article-content.html`).
     - Public vs Contributor link boundary: The **10 public pages** published to `site/` (`getting-started/{architecture,installation}.md`, `operate/{github-action,github-app,cli}.md`, `walkthroughs/declarative-taskpack.md`, `contracts.md`, `controller.md`, `pi-runtime-evaluation.md`, `decisions.md`) must never link to any of the **12 repository-only pages** (`development.md`, `contribute/*.md`, `adr/*.md`). Repository-only pages may link to public pages and to each other.
  5. **Diagrams**: Pair committed SVG diagrams under `docs/assets/diagrams/*.svg` (styled with Loopwright's Indigo-Violet `#5B4B9E`, Teal-Cyan `#3B8EA5`, and Warm Amber-Gold `#D89B48` palette, explicit `viewBox`, readable `>= 12px` labels, max 9 nodes) with a hidden `<!-- mermaid ... -->` source comment immediately below the image reference so humans get crisp rendering and maintainers keep editable graph structure.
- Add `references/page-map.md`: Canonical inventory of all 22 `docs/` pages, their group, whether published to `site/` (`10` published across `Getting Started`, `Operations`, `Walkthroughs`, and `Configuration`; `12` repository-only under `Contribute` and `Architecture Decisions`), exact H1 title, `navigation.yaml` label, line budget, primary audience, and owning source package/spec.

#### 2.2 `scripts/check-docs.mjs`
- Upgrade `checkDocs({ repoRoot, mode })` (`--strict` default for `npm run lint:docs`; `--report` prints grouped summary diagnostics and exits `0` for audit inspection; unknown `-`-prefixed CLI flags exit `2`) to validate all existing structural/link/anchor/module-map checks PLUS:
  1. **Heading caps**: Every `##` / `###` / `####` heading on `docs/**/*.md` (excluding `docs/README.md`) has zero interrogative words, and either matches `^Step [0-9]+: ` with `<= 4` words after the colon (`<= 38` chars total) or has `<= 4` words and `<= 32` characters.
  2. **Section & line caps**: Every non-index `docs/**/*.md` page has `<= 10` `##` sections (excluding `## Contents`), `getting-started/architecture.md <= 200` lines, `adr/*.md <= 220` lines, and all other non-index `docs/**/*.md` pages `<= 400` lines.
  3. **Prose paragraph caps**: Outside fenced code blocks, HTML comments, tables, blockquotes, list items, headings, and the trailing `\n---\n\n**See also**` reading footer, every contiguous prose paragraph is `<= 5` lines and `<= 500` characters.
  4. **Table header & cell discipline**: Every Markdown table header cell has `1–3` words (`<= 24` chars), contains no banned articles (`a`, `an`, `the`), demonstratives (`this`, `that`, `these`, `those`), or interrogatives, has consistent column counts across separator and data rows, and has cells `<= 180` characters.
  5. **Banned AI filler phrases**: Reject AI filler words/phrases (`seamlessly`, `delve`, `tapestry`, `leverage`, `utilize`, `cutting-edge`, `empower`, `it is worth noting`, `in order to`, `this page describes`, `this document describes`, `comprehensive guide`) case-insensitively in `docs/**/*.md` prose.
  6. **Pretty YAML discipline**: Inside ```` ```yaml ```` / ```` ```yml ```` fenced blocks across `docs/**/*.md` and `examples/*.md`, reject tabs, reject 4-space top-level indentation drift where 2-space YAML is expected, and reject embedded multi-line JSON object blobs (`:\s*[|>][-+]?\s*\n\s*\{`); also reject ```` ```json ```` configuration blocks in `examples/controller.md`.
  7. **Reading footer & Site publication link boundary**: Enforce `\n---\n` + `**See also** — [Title](target) (description)` (with `·`-separated items, each carrying a parenthetical description) across all non-index `docs/**/*.md` pages, enforce `**Next** → [Title](target) — description` on all 10 `site/`-published pages, and reject any Markdown link from the 10 `site/`-published `docs/` pages targeting `development.md`, `contribute/*`, or `adr/*`.

#### 2.3 `loopwright-issue-pr` (`.agents/skills/loopwright-issue-pr/SKILL.md`)
- Expand with complete Loopwright governance rules:
  - Issue prefix/label/type mapping (`[Bug]`/`bug`/`Bug`, `[Feat]`/`enhancement`/`Feature`, `[Docs]`/`documentation`/`Task`, `[Cleanup]`/`cleanup`/`Task`, `[Question]`/`question`/`Question`, `[TODO]`/`todo`/`Task`), `<= 80`-character title cap, template selection from `.github/ISSUE_TEMPLATE/*.md`, explicit warning that `.github/ISSUE_TEMPLATE/*.md` YAML frontmatter is stripped only by GitHub's web UI (so `gh issue create` MUST strip frontmatter and pass `--label` and `--type` explicitly), and explicit prohibition of `mcp__github__create_issue` when issue type/template metadata is required.
  - Pull Request rules: Conventional Commit title (`feat(<scope>): ...`, `fix(<scope>): ...`, `docs(<scope>): ...`, `refactor(<scope>): ...`, `test(<scope>): ...`, `chore(<scope>): ...`) `<= 80` chars, `.github/PULL_REQUEST_TEMPLATE.md` structure, `/kind` and `/area` commands, exact issue-linking verbs (`Fixes #N` for full resolution, `Addresses #N` for partial progress, `Relates #N` for context), mandatory `Signed-off-by: Name <email>` DCO trailer, secret/path hygiene (`0` host paths, `0` internal coordination refs, least-privilege `.github/workflows/`), and verification gate evidence before PR creation.

#### 2.4 `loopwright-release` (`.agents/skills/loopwright-release/`)
- Add `.agents/skills/loopwright-release/agents/openai.yaml`:
  ```yaml
  interface:
    display_name: "Loopwright Release"
    short_description: "Run explicit-only SemVer2 release verification and tagging for Loopwright"
    default_prompt: "Run the Loopwright release preflight and verification checklist for version vX.Y.Z."
  policy:
    allow_implicit_invocation: false
  ```
- Expand `.agents/skills/loopwright-release/SKILL.md` with YAML frontmatter (`name: loopwright-release`, `description: ...`, `disable-model-invocation: true`, `allowed-tools: Bash, Read, Grep, Glob, Edit, Write, AskUserQuestion`), SemVer2 tag regex `^v[0-9]+\.[0-9]+\.[0-9]+(-rc[0-9]+)?$`, three execution modes (`Interactive`, `Auto` preflight, `Unpublished-Tag Recovery`), and deterministic Phases 0–7:
  - Phase 0: Preconditions (clean `main`, exact SemVer2 tag validation, tool availability, valid `.github/workflows/` release pipeline).
  - Phase 1: Workspace version & lockfile consistency audit (`package.json` across root + 9 workspace packages, `action.yml`).
